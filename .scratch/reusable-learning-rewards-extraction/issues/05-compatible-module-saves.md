# 05: Load and save module-owned state compatibly

**What to build:** A player can launch with an existing money save, see the same learning and Garage progress, make a normal free selection and reload it through the new app-composed aggregate. Saves remain coherent and app identities stay isolated.

**Blocked by:** 03, Prefactor learning progression and Trophies without changing play; 04, Prefactor currency, Garage purchases and Goals.

**Status:** ready-for-agent

**Category:** enhancement

**Design basis:** Reusable learning, currency, and rewards design decision 06, Save compatibility and isolation, together with decisions 01 and 08. Its representative fixtures and accepted newer-version limits are required, not optional examples.

- [ ] The live money app decodes/encodes module-owned learning, currency, Garage and Trophy state through an app-specific adapter while retaining schema version 4, existing field names and storage key `mtm2-save`. Reusable modules do not depend on the legacy aggregate save type.
- [ ] Independently specified synthetic version-1/2/3/4 fixtures from ticket 01 decode, encode and reload to their expected player states using a fixed supplied day. Preserve full valid current state, null-Body setup, all Goal kinds, per-Body fits/Colours/Door Numbers, Legendary ownership and Trophy dates/counters.
- [ ] Preserve historical migration order, starter/default fits, Red/default Door Numbers, validated ownership, invalid/unowned-fit recovery, Goal clearing, filtered last-ten learning windows and validated version-1/2 learning-Trophy backfill. Do not invent historical streak/Round/day counts, redate known Trophies or add new counter/date repairs.
- [ ] Add the approved red-green recovery case for an unsafe saved Bolt integer: default only the balance to zero and retain unrelated valid state. Other invalid balances retain existing targeted recovery. Live arithmetic still rejects invalid transactions rather than silently repairing them.
- [ ] A missing/unreadable/malformed save or blocked read yields fresh in-memory state without deletion or a load-time write. Preserve best-effort known-field reading of newer versions; a later accepted action writes version 4 and may discard unknown fields, as explicitly accepted in the design.
- [ ] Publish the complete validated aggregate before enabling player actions. An initial load cannot later overwrite newer actions. No load resumes a Round/checkout, repeats completion, triggers purchases or presents success effects.
- [ ] The new commit seam publishes one coherent aggregate and requests one complete snapshot per accepted coordinated action. Rejected/calculation-failed proposals publish/save nothing. Ordered backing writes cannot let an earlier snapshot overwrite a later publication, including with an asynchronous test adapter. Prove this through the free-selection journey here; tickets 06-08 own routing the remaining purchase, practice and checkout action families through it.
- [ ] Serialization/write failure retains committed memory. A later successful action saves the full latest state, and restart reads the last successfully stored snapshot. Keep best-effort persistent-storage permission behind the backing adapter without introducing retries or recovery UI.
- [ ] Demonstrate a live free Body/fit selection through save/reload without currency effects, retaining compatibility facades for action families replaced in tickets 06-08. No old and new writer may both persist the same action.
- [ ] Two explicit compositions sharing one fake store read/write only their own stable keys; a fresh second composition ignores a populated money save and neither app imports the other's balance/progress. There is no shared default/fallback to the money key, and old Monster Cup keys remain ignored.
- [ ] Red-green tests observe adapter results, aggregate publications and complete fake-store snapshots, never real player storage or private write queues. Focused tests and typechecking pass and existing CI gates remain green.

**Out of scope:** Version/key changes, resetting data, automatic imports, durable receipts, multi-tab merging, cross-app sync, native data migration or real browser-save migration.
