# 06: Commit Bolt purchases and immediate fitting together

**What to build:** Tapping an affordable Mod, Body or Colour buys and applies it as one committed action. The screen and reloaded save never show a charge without ownership, or ownership without the immediate fit/selection and Goal update.

**Blocked by:** 05, Load and save module-owned state compatibly.

**Status:** ready-for-agent

**Category:** enhancement

**Design basis:** Reusable learning, currency, and rewards design decisions 03, Currency, purchases and ownership; 06, Save compatibility and isolation; and 08, Extraction evidence and handoff.

- [ ] Every live Bolt-purchase tap routes through app coordination that reads current aggregate state, asks Garage for its proposal, validates the cost with currency and synchronously publishes both proposed states together. No asynchronous gap, caller-chosen price or cached proposal authorises payment.
- [ ] With 16 Bolts and a selected 15-Bolt Mod Goal, purchase commits balance 1, ownership, immediate fit and cleared selection in one publication and one stored snapshot. Reload reproduces the combined state before purchase presentation runs.
- [ ] A bought Body commits ownership and the switch together. A bought Colour commits ownership, the current Body's Colour, any required Plain-Paint fallback and Goal clearing together. Preserve all per-Body state and current prices.
- [ ] Owned Mod/Colour fitting, owned Body switching, default selections and Door Number edits remain free app-coordinated actions. A direct purchase request for an owned item rejects without charging, refitting or clearing another Goal.
- [ ] Re-evaluate affordability/eligibility from the latest state on each tap. Insufficient funds, changed state, invalid/overflowing cost, currency rejection or unexpected pre-publication calculation failure changes and saves none of that action's proposals.
- [ ] Storage failure after acceptance retains the combined in-memory purchase. A later accepted action saves it; restart before recovery sees only the last successful snapshot. No refund/revoke path runs because persistence failed.
- [ ] UI speech/celebration receives only the committed result and cannot repeat the purchase. Remove the old split debit/unlock/fit write path as its replacement goes live, keeping one writer per action and the app usable.
- [ ] Red-green tests use real currency/Garage rules and approved app-purchase/persistence seams, observing aggregate snapshots and rendered results. Include Mod, Body, Colour, free-action, rejection and stale-display cases. Focused tests/typechecking pass and existing CI gates remain green.

**Out of scope:** Legendary cash checkout, changing prices, currency branding changes, a new purchase protocol or receipt ledger, production deployment and real player saves.
